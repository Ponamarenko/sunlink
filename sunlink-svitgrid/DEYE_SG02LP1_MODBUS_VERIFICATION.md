## 2. Применимость карты к точной модели

### Что подтверждено по модели
- Целевая модель: **`Deye SUN-12K-SG02LP1-EU-AM3`** (single-phase, LV battery). Семейство: `SUN-7.6/8/10/12K-SG02LP1-EU-AM2/AM3` (источник 1).
- **3-й MPPT:** у линейки 10/12K заявлен 3-й MPPT (2/3 MPPT в семействе; 7.6/8K — 2 MPPT). Следовательно, для 12K параметры **PV3** (напряжение/ток/мощность) релевантны и не должны игнорироваться; для 7.6/8K — неприменимы (источник 1, источник 4).
- **AM2 vs AM3:** официальное пользовательское руководство в задаче охватывает AM3 (`...SG02LP1-EU-AM3...`), datasheet на странице — `AM2/AM3` совместно; **различия Modbus-адресов/масштабов между AM2 и AM3 в открытых проверяемых данных не подтверждены** (C/неизвестно). Перенос без проверки недопустим.
- **Семейство SG02LP1 — отдельная карта:** источник 4 явно отделяет SG02LP1 от SG01LP1/SG03LP1 и от SG04LP3/SG05LP3/HP3 (другие диапазоны/адреса ключевых полей, свой TOU-блок). Регистры других серий **нельзя переносить** по сходству названий.

### Unit ID / Slave ID
- В текущем коде/конфигах: `slave_id = 1` (`server/deye_gateway.py`, `CONFIG.modbus.slave_id`; исторически то же в SunPortal). 
- Для NA111-E (Modbus TCP↔RTU шлюз, TCP Server, Modbus TCP to RTU Open / Simple, RS485 9600 8N1) фактический **Unit/Slave ID инвертора на шине RS485 не подтверждён** (зависит от настроек инвертора). 
- **Статус:** значение `1` — **предположение/дефолт (C), требует проверки на устройстве**. Неверный Unit ID даёт отсутствие ответов/ошибки, но не повреждает устройство при чтении.

### Порядок слов (32-бит)
- В `server/deye_gateway.py` DWORD собирается как `low + (high << 16)` (регистр `address` = low word, `address+1` = high word). 
- Источник 4 для SG02LP1 указывает 32-битные счётчики (напр. Total Production 96,97; Total Battery Charge 72,73) как пары регистров, но явный low/high порядок в извлечённом фрагменте не зафиксирован как однозначно верифицированный для AM3. 
- **Статус:** порядок `low word first` — **не подтверждён (C)**; ошибочный порядок даёт правдоподобные, но неверные значения энергии.

## 5. Совместимость с текущим окружением

### pymodbus
- **Локальная рабочая среда (где запускался аудит):** `pymodbus 3.16.2` (`python3 -m pip show`).
- **Сервер 192.168.25.20 (`/opt/sunlink/backend`):** пакет `pymodbus` в системном `pip` **не найден** (проверка read-only); активный `simple_svitgrid.py` Modbus не использует.
- **Требования драйвера:** `server/requirements.txt` фиксирует `pymodbus==3.6.2`, но фактическая установленная локально версия — 3.16.2 (расхождение).
- **Совместимость вызовов:** `server/deye_gateway.py` использует `client.read_holding_registers(..., count=N, device_id=...)` / `write_register(..., device_id=...)`. В современных pymodbus 3.x предпочтителен `device_id` (и/или `slave=` в старых API); старый SunPortal-код использовал `slave_id=` (несовместимо/рискованно). Для **3.16.2** текущая форма с `device_id` ближе к актуальному API, но **нужна целевая проверка на версии, которая реально будет запускать сервис** (без установки/обновления сейчас). Рекомендация: обертка совместимости (пробовать `device_id`/`slave`) и явная фиксация версии в окружении деплоя.

### Ebyte NA111-E (заданные параметры, не менялись)
- IP `192.168.25.15`, TCP `502`, UART `9600 8N1`, режим **TCP Server, Modbus TCP to RTU Open, Modbus Simple**. 
- Влияние на драйвер: нужен стандартный Modbus TCP клиент к `502`; корректность `Unit ID` и соответствие режиму (прозрачная трансляция TCP↔RTU) **не подтверждены** чтением с устройства. При `Simple/Open` режиме поведение кадрирования/ответов следует подтвердить на первом read-only прогоне (вне данного этапа).

### Текущий формат API SunPortal/SvitGrid (`:8000`, `svitgrid.service`)
- `GET /api/v1/health` → `{status,timestamp,active_connections,uptime,inverters_count,online_inverters}`.
- `GET /api/v1/inverters` → `{"inverters":["INV001"]}`.
- `GET /api/v1/inverters/{id}/status` → метаданные инвертора (без вложенного `data`).
- `GET /api/v1/inverters/{id}/data` → плоский объект данных (текущие ключи симуляции: `voltage_dc,current_dc,power_dc,voltage_ac,current_ac,power_ac,frequency,temperature,efficiency,state,error_code,battery_soc,battery_voltage,grid_voltage,grid_frequency,energy_today,energy_total,power_peak,operating_hours,firmware_version,serial_number,device_id`).
- `GET /api/v1/inverters/{id}/telemetry?hours=` → `{inverter_id,hours,data:[...]}` (элементы — копии data + `timestamp`).
- `GET /api/v1/system/stats` → `SystemStatsResponse` (`total_inverters,online_inverters,offline_inverters,total_power,total_energy_today,total_energy_total,system_efficiency,uptime`).
- WS `/api/v1/live` присутствует в коде (симуляция). `GET /api/v1/live` — 404 в текущем состоянии.

### Что реально ожидает Android (`ApiService.kt`, `MainViewModel.kt`, UI)
- **Основной путь:** `GET api/v1/inverters` → для каждого `GET api/v1/inverters/{id}/data`, merge нескольких инверторов; при отсутствии — `api/v1/system/stats` как fallback (`total_power` → `p_sun`).
- **Альтернативы:** `GET api/live/raw`, `GET live` (в т.ч. по абсолютному URL), в т.ч. fallback на `http://192.168.25.20:8000/` и gateway `http://192.168.25.20:8800/live|api/live/raw`.
- **Парсинг:** принимает плоский JSON или вложенный `data` с `{value,unit}` (`flattenGatewayData`), маппит алиасы: `p_sun←power_dc|pv_power`, `p_load←load_power|home_power|power_ac`, `batt_soc←battery_soc|soc`, `p_batt←battery_power|bat_power`, `p_grid←grid_power|grid_inverter_power`; UI использует также `p_string1-3`, `pv{1-3}_voltage/current/power`, `grid_voltage_l1`, `battery_voltage/current/temp`, `energy_today/total`, `power_ac/dc`, `voltage_dc`, `temperature` и др.
- **Вывод по совместимости:** Android гибок к ключам (алиасы/merge/fallback). **Внешний API-контракт `:8000` `/api/v1/*` менять нельзя**; безопаснее всего сохранять текущие эндпоинты/формы и наполнять их реальными значениями + совместимыми ключами-алиасами. Отдельный gateway-формат (`/live`, `/api/live/raw`) можно сохранять параллельно, не ломая `:8000`.

### Как заменить mock реальным источником без изменения внешнего API
- В `simple_svitgrid.py` оставить маршруты, модели ответов и `INV001`-идентичность; заменить генерацию/хранение `inverter_data[INV001]["data"]` и производных полей на чтение из read-only Modbus-адаптера (внутренний модуль/процесс) с маппингом в **те же ключи** (`power_dc, power_ac, voltage_dc, voltage_ac, current_dc, current_ac, battery_soc, battery_voltage, grid_voltage, grid_frequency, energy_today, energy_total, temperature, state, error_code, ...`) плюс вычисляемые/агрегированные значения; при ошибке — `online=false`, `last_update`/`state` отражают недоступность, без падения сервиса. `system/stats` и `telemetry` считать от реальных (или кэшированных/последних известных) значений, сохраняя формат.

## 6. Список ошибок и неподтверждённых мест текущего драйвера (`server/deye_gateway.py`)

1. **Карта/адреса (не подтверждены для SG02LP1-AM3 или расходятся с ист.4):** `182 battery_temp` (вместо/наряду с 90/91), `151,175,176`, энергосчётчики `60,63,74,76,78,80,84,85` (нет подтверждённых 108,96-97,72-73), `103,104`, семантика `166/167` vs `169/167/172`.
2. **Отсутствуют подтверждённые для SG02LP1 поля:** `91 AC temp`, `169 total grid power` (и корректный масштаб/знак), `108 daily PV`, `96-97 total PV`, `72-73 total battery charge`, полный корректный TOU 248–279.
3. **TOU-раскладка:** `tou_soc_1` в коде на `256`, в ист.4 для SG02LP1 — `268`; слоты 257/258 не сверены.
4. **DWORD порядок слов:** фиксирован `low + (high<<16)` — **не подтверждён**.
5. **Знак/направление:** `battery_power/current`, `grid` мощности — направление import/export, charge/discharge **не подтверждено**; балансный `p_grid` выдаётся как значение без метки «расчётное».
6. **Slave/Unit ID:** `1` — предположение.
7. **Совместимость окружения:** `requirements.txt` pin `pymodbus==3.6.2`, фактически локально 3.16.2, на сервере пакет не обнаружен; нужен воспроизводимый runtime.
8. **Конфиг рассинхронизирован:** `server/config.yaml` (`192.168.1.100`, `server.port=8000`, logging path) не соответствует коду/целевому устройству и кодом напрямую не используется.
9. **API-контракт gateway ≠ `:8000`:** `/live`, `/api/live/raw`, write/emergency — отдельный интерфейс; интеграция в `svitgrid.service` отсутствует.
10. **Безопасность (для будущего):** CORS `*`, write/emergency без аутентификации (на read-only этапе записи недопустимы в принципе).

## 7. Рекомендуемая архитектура реального read-only Modbus-адаптера

**Принципы:** read-only, без записи в регистры; один источник правды по карте (подтверждённой); изоляция от текущего API-контракта; деградация без падения.

1. **Слой чтения (Modbus reader):** модуль, выполняющий только `read_holding_registers` с подтверждённой картой (адрес, `count`, тип, знак, масштаб, порядок слов, имя). Параметры подключения (`host,port,timeout,unit_id`) — из конфига/ENV. Таймауты, ограничение частоты опроса, повтор с backoff, защита от наложения запросов (RS485/шлюз).
2. **Слой нормализации:** преобразование raw→engineering values, нормализация знаков (charge/discharge, import/export) по подтверждённым правилам, пометка происхождения (`measured` vs `estimated`) для `p_grid`/агрегатов; вычисления (напр. сумма PV1-3) только из подтверждённых входов.
3. **Кэш/состояние:** последний успешный снимок + `timestamp` + `online/error`; отдача кэша при кратковременных сбоях, явный `offline` при длительной недоступности (без залипания «успеха»).
4. **Адаптер в `simple_svitgrid.py` (`:8000`):**
   - сохранить все существующие `/api/v1/*` эндпоинты и формы JSON;
   - `get_inverter_data/status/telemetry/stats/health` формировать из нормализованного снимка `INV001`, маппя в текущие ключи (`power_dc/power_ac/voltage_dc/.../energy_today/...`) и при необходимости добавляя совместимые алиасы, которые уже понимает Android;
   - не менять количество инверторов/`INV001` и поведение 404 для чужих id без необходимости.
5. **Опционально (параллельно, без замены `:8000`):** существующий gateway `:8800` как диагностический read-only источник (`/live`, `/api/live/raw`) — только после приведения карты; write/emergency отключить или жёстко ограничить.
6. **Наблюдаемость:** структурированные логи ошибок Modbus (без спама значениями при каждом тике), счётчики успех/ошибка, последняя причина недоступности — для первого безопасного прогона.

## 9. Что пока нельзя безопасно использовать без проверки на физическом устройстве

- **Любые адреса/масштабы/знаки, не подтверждённые официально для AM3:** в первую очередь `182` (battery temp), `151,175,176`, `60,63,74,76,78,80,84,85`, `103,104`, `166/167/172` как окончательная семантика мощности сети, TOU-слоты кроме явно сверенных.
- **Unit/Slave ID = 1** (может не совпадать с настройкой инвертора).
- **Порядок слов 32-бит (DWORD)** и корректность сборки энергосчётчиков.
- **Направление знаков** (импорт/экспорт сети, заряд/разряд АКБ) и соответствие `169` масштабу `x10` для SG02LP1.
- **Различия AM2 vs AM3**, влияние прошивки/ревизии.
- **Режим работы NA111-E** применительно к конкретным кадрам/ответам (хотя типовой Modbus TCP клиент ожидаем).
- **Любые операции записи** (`/write`, TOU/лимиты/управление) — до полной верификации адресов и отдельного разрешения.
- **Балансный `p_grid = p_load - p_sun - p_batt`** как эквивалент показания CT/счётчика (может расходиться при неучтённых потоках/ошибках карты).

## 10. Краткий вывод

- **Можно ли уже реализовывать read-only драйвер?**  
  **Условно да, но только как осторожный pilot-read с ограниченным набором полей и под отдельным разрешением на первый read-only прогон.** Полноценную/достоверную замену mock на реальные данные «вслепую» делать нельзя: официальная Modbus-карта для `SUN-12K-SG02LP1-EU-AM3` в этом аудите не подтверждена, slave ID/word-order/знаки и часть адресов не верифицированы. Реализацию следует начинать с минимального read-only набора регистров уровня уверенности **B** по семейству SG02LP1, с маркировкой рассчитанных значений и с обязательной сверкой на устройстве.

- **Какие регистры достаточно подтверждены (уровень B, семейство SG02LP1, не A для AM3)?**  
  PV: `186,187,188` (power), `109-114` (V/I). Батарея: `183` (V, 0.01), `184` (SOC), `190` (power, S), `191` (current, S, 0.01, знак C). Температуры: `90` (DC), `91` (AC). Сеть: `150` (grid V L1); `169` (total grid power, **scale 10 по ист.4 — требует проверки**) / `167,172` (CT-контекст) — с оговорками. Энергия: `108` (daily PV, 0.1), `96,97` (total PV, U_DWORD, 0.1), `72,73` (total batt charge, U_DWORD, 0.1). TOU: блок `248–279` (в т.ч. enable 248, time1 250, SOC1 268) — **раскладку слотов нужно сверить целиком**.

- **Какие параметры пока нельзя считать достоверными?**  
  Slave/Unit ID; порядок слов DWORD; знаки/направления мощностей; семантика `166/167/172/169` в конкретной установке (CT/без CT); адреса, используемые сейчас в коде, но не подтверждённые ист.4 (`182,151,175,176,60,63,74,76,78,80,84,85,103,104` и смещения TOU-слотов 256/257/258); различия AM2/AM3 и влияние прошивки; любые счётчики/поля, не сверенные с показаниями инвертора.

- **Что конкретно нужно сделать следующим шагом (после получения разрешения)?**  
  1) Провести **первый разрешённый read-only** сеанс к `192.168.25.15:502` (минимальный набор: `184,183,190,191,186,187,188,109-114,150,90,91,108,96-97`) с перебором/подтверждением `Unit ID` и проверкой sanity значений. 2) На фактических ответах подтвердить word-order DWORD, знаки, масштаб `169` (если читается) и соответствие 12K/3MPPT. 3) Зафиксировать проверенную карту, затем точечно обновить ридер и интегрировать в `simple_svitgrid.py` с сохранением `/api/v1/*` контракта, бэкапом и рестартом только `svitgrid.service`. 4) Write/TOU/управление не включать.
