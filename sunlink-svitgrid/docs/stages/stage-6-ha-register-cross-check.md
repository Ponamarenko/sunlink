### Модель датчика Sunsynk (sensors.py)

```python
val = unpack_value(regs, signed=self.factor < 0)
val = int_round(float(val) * abs(self.factor))
```

- `factor > 0`: регистр декодируется как **unsigned**, значение = raw × factor
- `factor < 0`: регистр декодируется как **signed** (two's complement), значение = signed_raw × |factor|
- Отрицательный `factor` не инвертирует результат — он только переключает знаковое декодирование

```python
# TempSensor
val = int_round((float(regs[0]) * abs(self.factor)) - self.offset)
# offset по умолчанию = 100
```

Температура: `raw × factor − 100`.

DWORD-регистры передаются кортежем адресов, например `Sensor((78, 80), ...)`, декод `struct.unpack("<2H", ...)` — порядок LW,HW.

## 4. Противоречия масштаба: reg 169 (grid_power)

Sunsynk `single_phase.py`: `Sensor(169, "Grid power", WATT, -1)` — масштаб ×1, знаковое декодирование.  
Lokalный адаптер: `RegisterDefinition(169, "grid_total_power", "S_WORD", 10.0, "W")` — масштаб ×10.

| Источник | Масштаб reg 169 | HA значение 0 W | Физическое чтение этапа 4 (raw=0) |
|---|---|---|---|
| Sunsynk single_phase | ×1 | 0 × 1 = 0 W | 0 × 1 = 0 W |
| Дете SG02LP1 adapter | ×10 | 0 × 10 = 0 W | 0 × 10 = 0 W |

HA значение 0 W не позволяет различить масштабы (0 × 1 = 0 × 10 = 0). Противоречие масштаба ×1 vs ×10 для reg 169 остаётся неразрешённым — требует физического чтения при ненулевом значении. **Код не меняется** без отдельного согласования.

## 5. Анализ температуры reg 182 (222 °C)

Sunsynk `TempSensor(182, "Battery temperature", CELSIUS, 0.1)` с `offset=100` по умолчанию:
```
value = raw × 0.1 − 100
222 = raw × 0.1 − 100  →  raw = 3220
```

Если применён override `offset=-100` (как упоминалось в контексте этапа):
```
value = raw × 0.1 − (−100) = raw × 0.1 + 100
222 = raw × 0.1 + 100  →  raw = 1220
```

В обоих случаях raw — подозрительно круглое число (3220 или 1220), а результат 222 °C не является физической температурой батареи.

**Выводы:**
- reg 182 не содержит температуру батареи для данной модели инвертора, либо содержит статус/код ошибки, интерпретируемый как температура.
- Значение 222 °C совпадает с наблюдением этапа 4 (поле «РЕГІСТР» 222.0 °C на экране, признанное нефизическим).
- Локальный адаптер корректно исключает reg 182 из `REGISTER_MAP` (unconfirmed для AM3, этап 2.5, пункт 30).
- Поля экрана инвертора (батарейный бокс 20.8 °C, отдельный экран 22.2 °C) относятся к другим датчикам, не к reg 182.

## 6. Анализ мощности: reg 175 (inverter), 178 (load), 190 (battery)

### Данные HA (один снимок)
- `inverter_power` (175) = 2084 W — Sunsynk: WATT, −1 (signed, ×1), raw = 2084
- `load_power` (178) = 208 W — Sunsynk: WATT, −1 (signed, ×1), raw = 208; Load L1 (176) = 208, Load L2 (177) = 0 → 208 + 0 = 208 ✓
- `battery_power` (190) = 1915 W — Sunsynk: WATT, −1 (signed, ×1), raw = 1915
- `grid_power` (169) = 0 W, `grid_ct_power` (172) = 0 W
- `grid_connected` (194) = False

### Баланс мощности (HA)
Инвертор отдаёт 2084 W, нагрузка потребляет 208 W. Разница 2084 − 208 = 1876 W должна идти либо в заряд батареи, либо в экспорт в сеть.

- `grid_connected = False` → системы от сети, экспорта нет, grid_power = 0 обоснованно.
- Если батарея заряжается (потребляет ~1876 W): нагрузка 208 + заряд ~1876 ≈ 2084 W ≈ inverter_power 2084 W ✓ (сходится с погрешностью ~39 W, вероятно потери/время).
- Sunsynk `single_phase.py` для reg 190 не имеет явного комментария о знаке, но `micro_hybrid_ess.py` говорит: `"positive = discharging"`. HA показывает +1915 W → по Sunsynk это разряд, что противоречит балансу (при разряде батарея добавляет мощность, а не потребляет).
- Локальный адаптер интерпретирует положительное reg 190 как заряд (этап 4: +434 W = заряд). При таком значении: нагрузка 208 + заряд 1915 ≈ 2123 W vs inverter 2084 W — близко, разница 39 W.

**Вывод:** данные HA внутренне консистентны при интерпретации reg 190 как **заряд батареи** (положительное = заряд, как в локальном адаптере), что противоречит документированной конвенции Sunsynk (`positive = discharging` для micro_hybrid_ess). Знак reg 190 требует сверки с экраном инвертора в момент синхронного измерения.

## 8. grid_power = 0 не является доказательством отсутствия потребления

- HA: `grid_power` (169) = 0, `grid_ct_power` (172) = 0, но `grid_connected` (194) = False, `load_power` (178) = 208 W, `inverter_power` (175) = 2084 W.
- Нулевое grid_power обосновано тем, что система от сети (off-grid) — нет соединения с сетью, 따라서 и нет импорта/экспорта.
- Это подтверждает вывод этапа 3–4: `reg 169 = 0` не доказывает отсутствия потребления; семантика регистра для SG02LP1-AM3 требует отдельного уточнения.
- Физическое измерение CT не подменяется расчётом `load − PV − battery`. Формула Grid Power не изменяется.
